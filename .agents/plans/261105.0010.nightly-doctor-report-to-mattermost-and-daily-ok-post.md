## Overview

The nightly doctor audit on hive-warden-01 (`.agents/scripts/doctor-nightly.sh`, shipped by
plan 261101.0007) reports through `tbot-cli` to Telegram. The owner moves that report to
Mattermost: one channel per project, for beacon `~beacon` on team `prorochestvo-dev`, server
`https://mhub.seilbekskindirov.dev`, through an incoming webhook. Only the nightly doctor job
moves; the beacon service, its Telegram bot and every other job are untouched.

The same change consumes backlog entry L.0006. Its content, moved here as required:

> **Heartbeat for the nightly doctor audit.** Raised 2026-11-02 in the review of plan
> 261101.0007. Severity P3. The nightly job on hive-warden-01 is silent when every source is
> healthy, so a cron entry that stopped running looks the same as a healthy night. The
> launcher reports its own aborts, but not a run that never starts. Worth deciding: a weekly
> "still running" message, or an external check of the newest run directory's age.

Owner decision (2026-11-05, supersedes the weekly heartbeat): every nightly run that has
nothing to report posts one short OK message to the same channel. A missing morning post is the
dead-job signal.

Scope, in one line each:

1. Transport: `send_message` posts `{"text": ...}` to the webhook with `curl`; `tbot-cli` is
   no longer called anywhere in the launcher.
2. Secret handling: the webhook URL is read from
   `/home/buddy/.config/beacon-doctor/mattermost.env` and never reaches argv, the
   environment of a child process, a log, or the run directory.
3. Message budget and format: the 4096 UTF-16 budget becomes 16000 Unicode code points; the
   report body is sent inside one fenced code block.
4. Daily OK post on every silent nightly run; no second cron line.
5. The fixture test keeps running in CI without network, with `curl` stubbed, and asserts the
   secret never leaks.
6. Owner-approved reinstall on warden.

## Assumptions

- **Webhook contract** (owner-verified on hive-warden-01): `POST` with a JSON body
  `{"text": "..."}` and `Content-Type: application/json` returns HTTP 200 (body `ok`). The
  webhook's display name, icon and channel are fixed server-side; the launcher sends `text`
  only.
- **The secret file exists** at `/home/buddy/.config/beacon-doctor/mattermost.env`, mode 600,
  owner `buddy`, holding exactly one line `MM_WEBHOOK_URL=https://<host>/hooks/<id>`. Agents
  never print, copy or edit it. The URL contains no whitespace, `"` or `\` (a Mattermost hook
  id is 26 lowercase alphanumerics).
- **Mattermost measures the post limit in runes** (Unicode code points:
  `utf8.RuneCountInString` against `PostMessageMaxRunesV2 = 16383`). Python's `len()` on a
  `str` counts the same unit. An incoming webhook whose text exceeds the limit is split by the
  server into several posts rather than rejected, so an exceeded budget degrades, it does not
  lose the report.
- **Mattermost renders Markdown and does not raise mentions or render links, images or
  Markdown inside a fenced code block.** Plain-text sections are rendered: `@channel`, `@all`
  and `@here` notify the whole channel, and `![](url)` makes every client fetch the URL.
- **`curl` on warden** is the distribution build at `/usr/bin/curl` (the owner's test POST
  used it) and supports `--disable`, `--config`, `--write-out '%{http_code}'`, `--fail`, `--noproxy`,
  `--connect-timeout` and `--max-time`. Task 5 records the version read-only before install.
- **bash on warden is 4.4 or newer** (already required) and Linux exposes process substitution
  as `/dev/fd/<n>`, which `curl --config` opens as a regular path.
- **`run.log` line formats are stable inputs**: every run writes `<ts> start run <dir>`, at
  most one `<ts> report <outcome>` line (`report ok-sent` on a silent run), and
  `<ts> finish failures=<n>` when it completes (`step_log` in the current launcher).
- The launcher's cron line (`0 22 * * *`, random start delay up to 1800 s) and state layout
  (`~/.local/state/beacon-doctor/`) do not change.
- `tbot-cli` and its credentials on warden stay where they are; removing them is not part of
  this plan.

     by `MM_WEBHOOK_URL=""`. The `unset` matters: a variable inherited from the environment
     keeps its export attribute after a plain reassignment, so without it the secret loaded
     later would reach every child process.
  2. New `load_webhook`: reads `MM_ENV` with a bash `while IFS= read -r` loop (never
     `source`, which would execute the file), strips one trailing `\r`, takes the first line
     beginning `MM_WEBHOOK_URL=`, and accepts the value only if `[[ $value =~ $re ]]` holds,
     with the pattern kept in a single-quoted local
     `re='^https://[^[:space:]"\\]+/hooks/[A-Za-z0-9]+$'` (an unquoted pattern on the
     right of `=~` is subject to bash quoting rules that silently change its meaning). It
     returns 0 on success and does not exit, so Task 5 can call it alone; the caller in
     `main` handles the failure. On a missing, unreadable or
     non-matching file it prints `mattermost webhook not configured: <MM_ENV path> missing or
     malformed; no run started` to stderr (path only, never the value) and returns 1. `main`
     calls `load_webhook || { FINISHED=1; exit 1; }` right after `rotate_cron_log` and before
     `wait_random_delay`, so a missing secret fails before the 30-minute wait and before
     the lock.
  3. New `mm_payload`: stdin text to stdout JSON via
     `python3 -I -c 'import json,sys; sys.stdout.write(json.dumps({"text": sys.stdin.buffer.read().decode("utf-8","replace")}, ensure_ascii=True))'`.
     `ensure_ascii=True` makes the payload pure ASCII (`\uXXXX` escapes), so its encoding
     does not depend on the locale under `LC_ALL=C`.

     at once when `MM_WEBHOOK_URL` is empty, builds the payload once, and makes at most two
     attempts 30 s apart (the current retry policy). Success is curl exit 0 **and** HTTP
     code `200`. Before logging, `code` is validated with `[[ $code =~ ^[0-9]{3}$ ]] ||
     code=invalid`, so only a three-digit status or `invalid` reaches the log. Each failed
     attempt logs `step_log mattermost "failed exit=<rc> http=<code>"`; curl's stderr is
     discarded and its body goes to `/dev/null`, so no curl diagnostic text (which could
     quote the URL) is ever written. `--disable` is the **first** curl argument: curl reads
     `~/.curlrc` unless `--disable` comes first, and a `.curlrc` with `--trace-ascii`,
     `--stderr` or `--verbose` would write the URL to disk.

       env file (it never writes the URL itself); reads stdin, appends the raw payload to
       `calls/mattermost-payload.txt`, and appends the decoded `text` plus `\n---\n` to
       `calls/mattermost-messages.txt` (python3); prints the HTTP code from

     - The `claude` stub also appends `env` to `calls/claude-env.txt`.

    mac-m1 is clean.
- Pitfalls & edge cases:
  - Never `export` the variable and never pass it in an `env VAR=...` prefix: both put it in
    `/proc/<pid>/environ` of every child, including `claude`. The `unset` at the top covers
    the inherited case.
  - `--restricted` confines `claude`'s file tools to `$RUN` and `$REPO`; `MM_ENV` must stay
    outside both (under `$HOME/.config/`), which `check_static` enforces.
  - The value must only ever be expanded inside the `<(printf ...)` process substitution.
    `printf` there is the bash builtin running in a subshell, so no process with the URL in
    its argv exists. Do not replace it with `echo` from a pipeline that could become
    `/bin/echo`, or with a here-string or here-document: bash before 5.1 backs those with a
    temporary file, which would write the secret to disk.
  - `timed` closes descriptor 9 only; the process-substitution descriptor must stay open
    across `gnutimeout` to `curl`, which it does. Do not add a blanket fd close to `timed`.
  - `curl` honours `HTTPS_PROXY`; `--noproxy '*'` keeps the report channel direct, the same
    invariant the beacon bot keeps in code (`Proxy: nil` in
    `internal/infrastructure/telegrambot/tbotclient.go`): the channel that reports failures
    must not share a failure mode with what it reports on.
  - `on_exit` can fire before `load_webhook` ran (for example `mkdir` fails): `send_message`
    then returns 1 silently, which is correct; the line in `cron.log` is the only trace.
- Complexity: Medium
- Code Example:
  ```bash
  # send_message TEXT: one Mattermost post through the incoming webhook, one retry after 30 s.
  # The URL reaches curl only as a config file on a process-substitution descriptor, so it is
  # never in an argv, an environment, or a file on disk.
  send_message() {
    local payload attempt rc code
    [[ -n "$MM_WEBHOOK_URL" ]] || return 1
    payload=$(printf '%s' "$1" | mm_payload) || return 1
    for (( attempt = 1; attempt <= 2; attempt++ )); do
      rc=0
      code=$(printf '%s' "$payload" | timed 60 curl --disable \
        --config <(printf 'url = "%s"\n' "$MM_WEBHOOK_URL") \
        --silent --fail --noproxy '*' --connect-timeout 10 --max-time 30 \
        -H 'Content-Type: application/json' --data-binary @- \
        --output /dev/null --write-out '%{http_code}' 2>/dev/null) || rc=$?
      if (( rc == 0 )) && [[ "$code" == 200 ]]; then
        return 0
      fi
      [[ "$code" =~ ^[0-9]{3}$ ]] || code=invalid
      step_log mattermost "failed exit=$rc http=$code"
      if (( attempt == 1 )); then
        sleep 30
      fi
    done
    return 1
  }
  ```

### Task 2: Mattermost message budget and format
- Description:

     in the body is replaced with `'`, so no text can close the fence. The `fail_run`,

       Assertions: exactly 16000 code points; more than 16000 bytes; first-time list falls
       back to `15 not listed`; the immediate list ends with `+<n> more` (the engineer records
       the measured `n`); the model text is clipped with `…`; header, both fence lines and
       the log line are kept.

       markup appear only between the two fence lines.

## Risks

- **Mattermost down or the hook revoked.** No report and no OK post; the failure is only in
  `cron.log` (`mattermost failed exit=<rc> http=<code>`) and the exit status. By decision there
  is no fallback; a missing morning OK post is the signal, and it is ambiguous between "did not
  run" and "could not post" until `cron.log` is read.
- **Push delivery.** A post in `~beacon` without a mention may not push to the phone,
  depending on the owner's channel notification settings. Confirmed on 2026-11-05: the test post
  reached the phone with push.
- **Server on the legacy 4000-rune limit** (an unmigrated `Posts.Message` column). A report
  above 4000 code points would then arrive as several posts, not be lost. Realistic reports
  are well under 4000; only the pathological fixture approaches the budget.
- **Mention suppression inside code blocks** is Mattermost behaviour, not ours. If a future
  server version changed it, the model text could ping the channel. The `markdown-inert` case
  checks only our side (the fence is intact); verifying the server side needs a live post with
  `@channel`, which this plan does not send.
- **curl diagnostics discarded.** A failing post is logged with exit code and HTTP status only.
  Accepted: curl's messages can quote the URL, and the exit codes (6 DNS, 7 connect, 22 HTTP,
  28 timeout) are enough to start from.
- **`$HOME/.local/bin` first on `PATH`** (existing risk): a stray `curl` there would receive
  the URL on its config descriptor. It is `buddy`'s own directory and holds only the
  `openrouter-cli` shim today.
- **Window between merge and reinstall.** The old launcher keeps posting to Telegram and sends
  one Telegram drift message; both are expected.

## Trade-offs

- **URL to curl through `--config <(printf 'url = "%s"\n' ...)`, payload on stdin** over
  `--config -` with the payload in a file. Stdin can carry only one of them; keeping the
  payload on stdin matches the owner's tested `--data-binary @-` form and needs no payload
  file, while the process substitution keeps the URL in a pipe: argv shows only `/dev/fd/63`,
  no file is written, and the expanding `printf` is a builtin. Reversal: write the payload to
  `$RUN/mattermost.json`, pass `--data-binary @file`, and feed the config on `--config -`.
- **Parse the env file, never `source` it.** Sourcing executes arbitrary content and makes
  `export` one typo away. Reversal: none needed; the file format is one line.
- **Strict URL pattern** (`https://`, no whitespace, `"` or `\`, ends `/hooks/<alnum>`): those
  are exactly the characters that would break the curl config quoting, and anything else
  means the file is not what the owner wrote. No mode or owner check on the file: the owner
  set it up and an extra refusal is an unrequested safeguard. Reversal: relax the regex.
- **Fail before the start delay when the secret is missing.** A run that cannot report is
  not worth 30 minutes and a lock; exit 1 lands in `cron.log`, and the missing morning OK post
  surfaces it the next day. Reversal: move `load_webhook` after `acquire_lock`.
- **Budget 16000 code points** over 16383: a round figure below the documented limit, so a
  header change does not need re-measuring; the unit is the one Mattermost counts. Lists get
  15000 so the overall clip can still bind (with the old 3000 it never would, leaving the
  clip path dead and untested); the model block keeps its 1500 cap, since its source is
  already capped at 1200 by the verdict schema. Per-list cap 60 covers all 56 active sources,
  so a full-fleet failure is listed in full instead of "+41 more". Reversal: change the four
  constants.
- **Whole body in one fence** over escaping Markdown or fencing only the model text. One rule,
  the post renders exactly like the Telegram text did, and mentions, links and images in
  untrusted text become inert. Cost: monospace and no clickable links (none are wanted).
  Reversal: drop the fence lines in `compose_message`.
- **OK post every silent night over a weekly heartbeat.** Owner decision 2026-11-05: one post a
  night in a project-only channel is no noise, and a dead job shows the next morning. Reversal:
  return in `decide_report`'s silent branch without posting.
- **Retry only when the server did not answer 4xx other than 429** (added in code review). A
  4xx means the hook is gone or the payload is refused, so a second attempt only costs 30 s; a
  429 is rate limiting, which a retry after 30 s can clear, so it retries once. A timeout or
  5xx still retries once; Mattermost incoming webhooks are not idempotent, so a post the
  server accepted after `--max-time` can appear twice. Accepted: a rare duplicate is cheaper
  than a lost report. Reversal: drop the `4??` check, or drop the retry.
- **`--noproxy '*'`.** One flag that keeps the report channel's egress independent of any
  proxy variables, the same rule the beacon bot follows. Reversal: drop the flag.
- **Backup of the running launcher on warden** over restoring from git. `cp -p` before
  install makes the reversal one `install` command with no dependency on the clone's state.
  Cost: one stray file until the owner decides on its removal.
