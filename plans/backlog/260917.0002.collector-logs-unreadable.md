# Current collector logs are unreadable to the SSH account

**Status: open.** Raised 2026-09-17, neither accepted into a plan nor dropped. Severity P3 —
it slows diagnosis, it does not break collection. Needs a host change, so it cannot be
actioned without the owner.

Diagnosing issue #146 on `qazaqmap.kz` meant reading the collector's own failure lines. They
were not reachable from the `aide` SSH account:

```
-rw-r--r-- root root  collector.00000001.log   <- readable, but rotated out on 2026-08-30
-rw------- root root  collector.00000002.log
-rw------- root root  collector.00000003.log   <- current
```

`sudo -n -l` for `aide` grants `nginx -t`, a handful of `systemctl` verbs, and
`journalctl -u beacon`; nothing that reads a file under `/opt/beacon/logs/`. The current
collector and notifier logs are therefore invisible, and `journalctl -u beacon` covers the
web service only — the collector is cron-driven.

The diagnosis was completed anyway, through three substitutes: the one rotated log that
happened to be mode 644, `http://127.0.0.1:8000/api/v1/sources` on the host for per-source
`last_success` / `last_run_at`, and the world-readable daily snapshot in
`/opt/beacon/backups/`. That worked because the failure was steady-state and three weeks old.
A transient failure visible only in the current log would not have been diagnosable at all.

Worth deciding, one of:

- **Group-read the log directory** — the `aide` account is already in `adm`, so
  `chgrp adm /opt/beacon/logs/*.log` plus a mode of 640 and a matching umask in the log
  writer would make current logs readable without granting anything executable.
- **A narrow `NOPASSWD` sudoers line** for reading under `/opt/beacon/logs/` only.
- **Accept it** and treat the local API plus the daily snapshot as the supported diagnosis
  path, documenting that in `deploy/README.md` so the next person does not rediscover it.

Both of the first two are writes on a production host and need explicit per-action approval.
